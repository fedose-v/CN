Техническая документация: Алгоритм кэширования HTTP прокси-сервера

## Введение

Данный документ описывает архитектуру и алгоритмическую реализацию подсистемы кэширования, входящей в состав разработанного HTTP прокси-сервера.

Основной целью внедрения кэширования является повышение производительности сети за счет:

  * Снижения времени отклика для клиента (Latency reduction).

  * Уменьшения объема трафика, передаваемого по внешним каналам связи (Traffic reduction).

  * Снижения нагрузки на целевые веб-серверы.

Реализованный алгоритм относится к типу дискового кэширования (Disk-based caching) с пассивной стратегией заполнения (On-demand caching).


## Архитектура подсистемы кэширования

За логику работы с кэшем отвечает класс CacheManager. Он инкапсулирует в себе все операции ввода-вывода (I/O) с файловой системой и предоставляет интерфейс для проверки наличия, чтения и записи данных.
Основные компоненты:

  * Идентификатор ресурса (Ключ): Полный URL-адрес запрашиваемого ресурса (строка).

  * Хранилище (Значение): Сериализованные данные HTTP-ответа (бинарный поток), сохраняемые в локальной файловой системе.

  * Механизм отображения (Mapping): Хэш-функция, преобразующая URL в уникальное имя файла.

## Алгоритм работы

Процесс обработки запроса с использованием кэша реализуется в методе ProxyHandler::ProcessRequest и состоит из следующих этапов:
### Этап 1: Идентификация запроса

При получении HTTP GET-запроса сервер извлекает URL. Данный URL является уникальным ключом для поиска в кэше.

### Этап 2: Генерация сигнатуры (Хэширование)


Поскольку URL может содержать спецсимволы, недопустимые в именах файлов (например, ?, /, :, &), а также иметь произвольную длину, используется механизм хэширования.

  * Используется стандартный функтор std::hash<std::string>.

  * Формула: Filename = "./cache/" + to_string(hash(URL))

  * Это обеспечивает константную длину имени файла и уникальность (с поправкой на крайне низкую вероятность коллизий хэш-функции для 64-битных значений).

### Этап 3: Проверка наличия (Cache Lookup)

Алгоритм проверяет существование файла с вычисленным именем в директории ./cache.

    Если файл существует и доступен для чтения → Cache Hit (Попадание).

    Если файл отсутствует → Cache Miss (Промах).

### Этап 4: Обслуживание запроса
Сценарий А: Попадание в кэш (Cache Hit)

  * Система открывает соответствующий файл в бинарном режиме (std::ios::binary).

  * Содержимое файла считывается в буфер оперативной памяти (std::vector<char>).

  * Данные отправляются клиенту немедленно, без обращения к удаленному серверу.

  * Обновляется статистика (инкремент счетчика Hits).

Сценарий Б: Промах кэша (Cache Miss)

* Прокси-сервер устанавливает соединение с целевым хостом.
* Отправляется запрос и ожидается ответ.
* Полученные данные сохраняются в буфер памяти.
* Синхронная запись (Write-Through): Данные из буфера записываются на диск в файл с сгенерированным хэш-именем. Файл создается или перезаписывается.
* Те же данные отправляются клиенту.
* Обновляется статистика (инкремент счетчика Misses).

## Обработка коллизий и многопоточность

Архитектура сервера выделяет отдельный поток (std::thread) на каждого клиента.

* Чтение: Множественные потоки могут одновременно читать один и тот же файл кэша (операционная система и файловая система допускают конкурентное чтение).
* Запись: В текущей реализации, если два клиента одновременно запрашивают один и тот же новый URL, может возникнуть состояние гонки (race condition) при записи файла. Однако, так как данные идентичны, это приведет лишь к тому, что файл будет перезаписан одинаковым содержимым (Last Write Wins), что не нарушает целостность данных для данной задачи.
* Статистика: Доступ к счетчикам попаданий/промахов защищен мьютексом (std::mutex) в классе StatisticsManager, что гарантирует корректность логов.
